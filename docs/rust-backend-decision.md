# Rust 后端的保留依据与性能决策

按新的取向，**结果一致性优先；逐模块评估速度、峰值内存与数值误差，有证据的收益才构成优化理由**。
当前保留 Rust 作为独立后端与无 Python CLI 的实现，不把语言本身当作加速或精度证明。
新增原生算法必须分别说明定义、实际部署需求、速度/内存/稳定性收益与维护成本。

## 已有实测说明什么

以下来自冻结快照的独立套件，不能混成项目总加速比：

| 工作量 | 参考 median | 原生 median | 参考/原生 | 解释 |
|---|---:|---:|---:|---|
| 真实CT已准备数组，完整L2公共调用 | 157.666 ms | 394.163 ms | 0.400× | 原生入口慢约2.50倍，性能缺口存在 |
| 同例真实CT，文件读取至导出L3 | 225.082 ms | 183.807 ms | 1.225× | 快约22.5%，未达到1.5×目标 |
| 二分类LR完整热运行 | 70.595 ms | 43.261 ms | 1.632× | 仅对声明合成表格流程成立 |
| Ridge完整热运行 | 38.245 ms | 38.985 ms | 0.981× | 接近同速，不称加速 |
| 已解码病理前端热运行 | 10514.620 ms | 2327.506 ms | 4.518× | 参考是冻结的小型Python规格，不是优化的WSI/图像引擎 |

原始记录和环境见[Radiomics报告](radiomics-benchmark-v2-results.md)及
[ML/Statistics与Pathology报告](learning-pathology-benchmark-v2-results.md)。
性能目标未达到必须保留为缺口；无Python部署通过不能替代慢路径的性能验收。

现有完整流程的进程RSS也给出一种不依赖加速的保留理由：二分类LR热运行参考/原生
为110.31/63.71 MiB，Ridge热运行为110.05/63.84 MiB（各7次的进程峰值中位数）。
后者耗时近似同速，而原生进程峰值约为参考的0.58倍。这个收益包括依赖加载和完整
工作流成本，不是对求解器单独分配量的证明；仍只限该冻结数据和环境。

## 为什么不能只按语言判断

PyRadiomics3.0.1的纹理矩阵和部分形态已有C扩展；参考路径也使用NumPy和SimpleITK。
这里的比较对象不是逐体素的纯Python循环。[PyRadiomics3.0.1官方说明](https://pyradiomics.readthedocs.io/en/v3.0.1/installation.html)

本项目的数组接口还有明确可见的传输设计成本：`from_array`、mask构造、`ImageSample`构造和
`extract`多次把大缓冲转换成JSON，进入Rust后解析，再把验证后的缓冲传回Python；
样本构造还会复制已有数据。Rust计算更快也可能被这些成本抵消。
PyO3调用和类型转换也需要单独分析，不能把所有开销归咎于GIL或Rust本身。
[PyO3性能说明](https://pyo3.rs/main/performance.html)

静态调用链不是耗时百分比证明。L2与L3有不同入口，不能相减就宣称某一步占用了差值；
具体阶段、纯Rust核与构造/序列化耗时由[独立边界诊断](native-performance-diagnosis.md)报告。
诊断原始记录与正式854条基准分开，不改其数据、定义、阈值或结果。

随后已实现一个[小范围Sample构造优化](sample-constructor-optimization.md)：保留全部
验证和owned响应，省去同步编码之前的两次临时深复制。同二进制/同CT的短对照中完整L2
中位耗时下降约17.38%，但lifetime peak RSS没有下降。因此只记录速度收益，不称内存
优化成功，也不据此宣布正式的相对参考1.5×目标通过。

## 保留Rust的条件

| 使用需求 | 当前决策 |
|---|---|
| 独立CLI、环境没有Python、上游需要Rust crate | 保留原生核心；这是实际部署需求，Rust是当前实现手段，并非唯一可选语言 |
| Python用户只关心某项任务速度 | 按同输入、同特征、同线程的实测选择显式后端；慢的原生入口不标为推荐加速路径 |
| 耗时接近，但峰值内存有可靠下降 | 可以保留原生路径；报告完整工作量RSS、共同启动成本、输入表示与是否流式，不能用一次低水位冒充峰值 |
| 数值稳定性或舍入误差改善 | 用独立高精度oracle和错误界证明；语义变化需单独profile，不能通过换参考或多打印小数位宣称更准 |
| Python/CLI需要共享定义、模型格式和预测来源验证 | 保留单一原生实现与薄适配，减少执行语义分叉；同时评估接口维护负担 |
| 成熟外部库已有能力而本包无独特需求 | 保留明确的可选适配，不为凑“全Rust”重复实现 |
| 经边界与内核诊断后仍无性能、部署或维护收益 | 不再以语言本身为理由扩展该原生部分，应考虑缩小职责或采用成熟实现 |

已经投入的开发量不是继续使用某种语言的理由。当前独立CLI和共享核心有已验证用途，
足以支持保留；它们不足以证明所有Python计算都应该迁入Rust。

Python层可以显式组合已有的外部提取后端与原生筛选/建模，不要求整条流程统一选Rust。
输入的ID、单位、特征定义、有效参数和来源必须保留。`rust/auto`仍不静默切换算法；
CLI仍只调用已支持的原生核心，不为混合后端引入Python运行时。

## 一致性、精度与内存怎样分别证明

一致性继续使用既定分层规则：ID、mask、计数矩阵和划分集合精确；确定性特征按冻结容差；
线性/Logistic同时检查预测、目标、梯度/KKT和收敛；森林使用声明的行为验收和原生可复现性，
不承诺不同库的同seed产生同一组树。速度或内存优化不能改变这些定义。

“更准”需要独立依据。对输入已经成为binary64的数，参考应从该浮点值精确建立Fraction或
高精度Decimal，而不是把用户原先想输入的十进制数当作实际输入。大offset小方差、消去、
极小概率和病态设计矩阵均可能揭示误差；Rust与Python都用float64时没有语言保证。
已有小型核对见[标量精度审计](scalar-accuracy-audit.md)。更小的舍入误差也不等于临床预测更准。

若更稳定的算法落在现有数值容差内，可以在原定义下验证兼容；若与冻结行为实质不同，
应先声明独立精度profile、参考与失效行为，默认兼容路径保持原定义。当前不新增占位高精度后端。

内存报告分别给完整进程峰值、加载基线与阶段观察。避免重复对象/JSON、复用拥有的buffer、
流式patch和分块图可以降低峰值，但不能取消必需验证或把内存搬到未计时的准备步骤。
原1.20×RSS工程保护上限不等于已证明节省内存，真正收益要单独量化。

## 后续优化先后顺序

1. 先减少大数组的重复JSON传输、构造和复制。考虑类型化缓冲或持有原生对象的边界，
   保持现有几何、非有限值、ROI、缺失标记和错误语义。
2. 再依据纯Rust阶段证据优化纹理计数、分配和重复工作；没有热点证据时不盲目并行化。
3. 用原公共API复测完整成本，包括构造、I/O和导出；只快一个内部核不能代替用户端加速。
4. 运行原数值验收和既定性能协议，保存冷/热/缓存状态、原始重复值、RSS及未达目标项。

这是一份保留范围和优化优先级决策，不是性能修复完成声明，也不改变 `rust/auto`
不会静默回退到Python参考算法的规则。
